# S6 중심의 독립 검증

AGENTS, CURRENT, 최신 RULES와 REQUIREMENTS를 읽고 검증할 범위를 정한다. 구현 담당자는 자기 범위, S6는 독립 검증, S1은 최종 수용을 맡는다.

- R-ID별 명령, 입력, 기대값 근거, 실제 출력/종료 코드, 결과 파일과 코드 위치를 연결한다. PASS/FAIL/NOT_RUN/HUMAN_CHECK를 사용한다.
- 핵심 계산은 구현과 독립된 작은 사례로 검산한다. 중요한 테스트가 의도된 오류를 잡는지 확인한다. 전체 대용량 실행은 필요할 때 자원 소유자와 조정한다.
- 첫 완주에는 대표 입력부터 출력까지, 개선 뒤에는 바뀐 부분과 회귀, 제출 전에는 HOW_TO_RUN 등 실제 안내 명령과 필수 흐름을 확인한다. 코드와 입력이 안 바뀐 검증을 의미 없이 반복하지 않는다.
- 적용 가능한 경우 잘못된 입력, 취소/중복/시간 경계, 불가능한 제약, 반복 요청/동시 수정과 실패 후 상태를 검토한다. 미구현 기능을 기대값에 슬쩍 넣지 않는다.
- 결함은 확인됨/의심/개선 의견으로 구분하고, 재현/업무 영향/우선순위/최소 수정 방향을 자기 SUB_RESULT에 남긴다. 수정은 코드 소유자에게 전달한다.
- S1이 EVIDENCE와 REQUIREMENTS를 갱신한다. S8에는 코드/테스트/실행 증거의 구분과 남은 한계를 전달하며, 예상 문항 작성은 S8이 맡는다.

## 자원과 제출 확인

시작과 중간에도 RULES의 환경 제약을 확인한다. RAM 16GB 안에서 실제 사용량과 무거운 작업을 보고 조정하며, 메모리 확인을 위해 설정을 바꾸지 않는다.
최종 제출 범위의 전체 용량 10GB 이하, 필수 파일, 저장 상태, 노출된 비밀값, 제공 README 보존과 실행 명령을 확인한다. `.git`이나 의존성 폴더가 용량 산정에서 제외된다고 가정하지 않는다. 용량을 줄일 때 실제 사용하지 않는 생성물인지 소유자와 확인하고 코드/근거를 임의 삭제하지 않는다.
제출 버튼과 완료 표시는 사용자가 확인한다. 오류가 나면 발생 시각/증상을 공식 문의로 전달한다. 자동 제출이나 실제 후속 서술형 답변에는 관여하지 않는다.

## 자동 점검 보조

S7 제출 문서는 기본 제출 예정 30분 전까지 검증하고, 이후에는 S8 설명 연습과 병행해 최종 변경/필수 오류만 점검한다. `python3 .probe-kit/scripts/pre_submit_audit.py --workspace .`에 실제 필수 파일별 `--require <경로>`를 추가해 읽기 전용 점검을 수행할 수 있다. 값은 숨기고 위치/유형만 보고하며 검색 제외/한도/오류를 확인한다. loopback 참조는 실제 서버 바인딩인지 직접 확인한다. 종료 0은 한정된 자동 점검 통과, 1은 용량/파일 실패, 2는 추가 확인 또는 미완료다. 수동 확인은 남아 있으므로 자동 점검 결과를 과제 전체 PASS나 무감점 보증으로 옮기지 않는다.
