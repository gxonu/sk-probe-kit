# 실행 순서 보조 요약

과제 진행의 시작점은 원본 기반 [foruser.md](../foruser.md)다. 이 문서는 시간 계산과 실행 순서를 빠르게 다시 볼 때 사용한다. 공식 안내와 실제 응시 화면이 우선한다.
각 단계는 담당자, 실행할 일, 남길 파일, 다음 단계로 넘어갈 조건으로 구성한다.
하네스의 설정과 도구는 준비된 그대로 사용하며 실제 과제에 필요한 작업에 시간을 쓴다.

## 0. 시작 직후: 시간과 환경 확인

응시자가 실제 시작 시각, 과제 제한 시간, 전체 마감, 후속 서술형 시간을 확인한다.
기존 안내는 과제 최대 180분, 질문 생성 대기 최대 10분을 계획에 반영, 서술형 30분이다.
날짜와 시각은 과거 문서에서 복사하지 말고 당일 화면을 CURRENT에 기록한다.

- 감독 연결과 장비 조건을 확인하고 실제 문제의 README, 제출 형식, 작업 폴더를 찾는다.
- 터미널에서 `pwd`로 과제 루트를 확인한다. 아직 하네스를 설치하지 않았다면 아래 순서로 진행한다.
- Git 저장소가 아닌 폴더여도 설치할 수 있다. 기존 .git을 만들거나 지우는 작업은 필요하지 않다.

## 1. 설치와 점검: 초기 5분 목표

과제 루트에서 각 명령이 성공한 것을 확인한 뒤 다음 명령을 실행한다.

```bash
probe_kit_dir="$(mktemp -d)"
git clone --depth 1 https://github.com/gxonu/sk-probe-kit.git "$probe_kit_dir"
bash "$probe_kit_dir/init.sh" . --dry-run
bash "$probe_kit_dir/init.sh" .
python3 .probe-kit/scripts/preflight.py --workspace .
codex
```

점검은 필수 문서, 스킬, Python, Bash, Git과 `codex --version`을 확인한다.
설치된 Codex의 설정이나 인증을 변경하지 않으며 업데이트하지 않는다.
PASS여도 감독 연결, 모델 사용 권한, 실제 과제 실행과 UI는 응시자가 확인한다.

이미 .probe-kit이 설치되어 있으면 먼저 preflight만 실행한다.
버전 충돌이 나면 기존 작업을 덮어쓰거나 삭제하지 않는다. 사용할 수 있는 현재 구성으로 진행하고 필요한 문서만 읽는다.
clone이 안 되거나 설치 문제가 5분 안에 해소되지 않으면 아래의 최소 진행 요청으로 과제를 시작한다.

## 2. 메인 세션 시작과 시간표 확정

메인 터미널에서 `codex`를 시작하고 `/model`로 실제 제공된 허용 모델을 선택한다.
모델 ID, 추론 수준, 개인 API 키를 강제로 넣지 않는다. 세션 수는 점수 기준이 아니다.

다음 요청의 시작 시각과 마감만 실제 값으로 채운다.

```text
[MAIN] 너는 이 과제의 통합 담당 세션이야.
.probe-kit/AGENTS.md와 .probe-kit/AGENTS.override.md, .probe-kit/docs/RULES.md,
.probe-kit/foruser.md, docs/handoff/README.md와 docs/handoff/CURRENT.md를 읽어.
실제 시작은 [날짜, 시각, 시간대], 전체 마감은 [날짜, 시각, 시간대]야.
화면의 과제 제한은 [분], 후속 서술형은 [분]이야.
plan_time.py로 시간표를 계산하고 CURRENT에 기록해.
내 세션 ID를 main으로 등록하고 공통 요구, 질문, 결정, 증거를 관리해.
README와 입력을 필요한 범위만 읽고 사실, 가정, 열린 질문,
사용자 행동, 성공 기준, 제외 범위를 정리해.
담당자 질문을 최대 3개씩 제시하고, 최초 구현 계획을 내가 승인하면 최소 흐름부터 진행해.
```

시간 계산 도구는 다음 형태로 실행한다. 아래 날짜는 기존 안내를 사용한 계산 예시이며 당일 값을 대체하지 않는다.

```bash
python3 .probe-kit/scripts/plan_time.py --start '2026-10-31T10:00:00+09:00' --hard-end '2026-10-31T14:00:00+09:00'
```

계산 원리:
- 과제 확정 한계 = 과제 시작 + 제한 시간과 전체 마감 - 질문 생성 여유 - 서술형 시간 중 더 이른 시각.
- 제출 시작은 확정 한계보다 기본 10분 앞선다.
- 기능 동결은 제출 시작보다 최대 30분 앞선다. 시간이 짧으면 간격도 줄인다.
- 첫 전체 흐름은 시작 후 최대 40분을 목표로 하며 기능 동결보다 늦지 않게 한다.
- 날짜나 시간대가 빠졌거나 남은 시간이 부족하면 계산을 실패로 처리한다. 실제 타이머가 더 짧으면 더 이른 시각을 따른다.

## 3. 문제 정의와 첫 합의: 기본 25분 안

| 담당 | 실행 | 남길 기록 | 다음 단계 조건 |
|---|---|---|---|
| 메인 | README, 데이터 구조, 기존 실행 명령 확인 | REQUIREMENTS의 사실과 가정 | 누가 어떤 결정을 할지 설명 가능 |
| 응시자 | 담당자 질문 전송과 답변 전달 | 질문 원문, 답변, 출처와 시각 | 중요한 모호함이 해소되거나 가정으로 표시됨 |
| 메인 | 답을 Q-ID → R-ID → 검증 방법에 연결 | QUESTION_LOG, REQUIREMENTS | 입력, 출력, 필수 조건, 제외 범위 명확 |
| 응시자와 메인 | 최소 구현 방식과 더 단순한 대안 비교, 최초 계획 확정 | DECISIONS | 첫 흐름의 완료 조건과 담당 파일 확정 |

질문은 현재 업무 → 실제 사례 → 우선순위 → 구체적인 입력과 기대 결과 순으로 좁힌다.
질문 수를 채우거나 답을 모두 기다리며 멈추지 않는다. 답과 독립적인 구조 확인과 재현 준비는 진행한다.
결과가 달라지는 미확인 조건을 임의로 확정하지 않는다.
담당자 답을 받으면 다음과 같이 전달한다.

```text
담당자의 답은 다음과 같아: [실제 답변]
출처와 받은 시각: [실제 값]
이 답이 바꾸는 요구, 구현, 테스트를 찾아 반영해.
새 선택이 생기면 업무 영향, 적용 조건, 재검토 조건을 결정 기록에 남겨.
```

## 4. 여러 세션 배정: MAIN + 작업자 1~2개 예시

통합 담당자는 공통 원장과 CURRENT를 관리한다. 작업자는 구현, 데이터 확인, 검토 등 필요한 역할을 맡는다.
worker-a와 worker-b는 예시 ID이며 역할과 개수는 고정하지 않는다. 원본의 명세와 결과 파일만 작업자별로 나눈다.
메인은 중요한 코드와 결과를 직접 확인하고 필요하면 구현도 한다.

메인에 요청:

```text
CURRENT에 worker-a와 필요하면 worker-b를 등록하고 겹치지 않는 쓰기 경로를 배정해.
각각 docs/handoff/sessions/<session-id>/TASK_SPEC.md에 작업 ID,
목표 하나, R-ID, 파일 범위, 제약, 검증 명령과 완료 조건을 적어.
공통 원장은 네가 관리하고 결과는 각 세션의 SUB_RESULT.md와 HANDOFF.md에 남기게 해.
```

응시자는 같은 과제 루트의 새 터미널에서 `codex`를 시작한다. worker-a에 전달:

```text
[SUB] .probe-kit/SUB_AGENTS.md와 .probe-kit/AGENTS.override.md, docs/handoff/README.md,
docs/handoff/CURRENT.md, docs/handoff/sessions/worker-a/TASK_SPEC.md를 읽어.
배정된 역할과 쓰기 경로 안에서 작업하고 실제 검증을 실행해.
질문이나 범위 변경이 필요하면 자기 인계 파일에 남겨 메인에게 전달할 경로를 알려줘.
결과는 자기 SUB_RESULT.md에 작업 ID, 명령, 출력, 상태, 코드 기준과 함께 기록해.
완료 또는 중단 시 자기 HANDOFF.md를 갱신해. 공통 원장은 직접 수정하지 마.
```

세션이 추가되면 worker-b처럼 고유 ID와 별도 폴더를 사용한다. CURRENT의 쓰기 범위를 먼저 나눈다.
검토 역할은 기본적으로 코드 읽기와 자기 결과 작성만 맡고 수정이 필요하면 메인에 전달한다.
두 세션이 같은 파일을 수정하거나 같은 개발 서버의 포트를 동시에 사용하지 않는다.
현재 MAIN을 교체할 때는 기존 MAIN의 인계를 수신한 후 CURRENT 작성 권한을 넘긴다.

## 5. 구현과 검증 반복: 첫 전체 흐름 40분 목표

각 반복은 명세 → 구현 → 실제 실행 → 메인 확인 → 원장 반영 순서다.

```text
[MAIN] docs/handoff/sessions/worker-a/SUB_RESULT.md와 해당 보고서를 읽어.
작업 ID가 현재 명세와 같은지 확인해.
변경된 핵심 코드와 실제 실행 결과를 확인하고 R-ID별 충족 상태를 갱신해.
실패나 미검증을 구분하고 다음 한 가지 목표를 배정해.
새 요구가 생기지 않았다면 합의된 범위의 수정은 반복 승인 없이 진행해.
```

첫 완료 기준은 대표 입력 하나가 요구된 출력까지 도달하는 것이다.
화면 과제라면 입력 → 처리 → 결과 확인의 핵심 동선을 먼저 완주한다.
데이터 과제라면 출력값, 건수, 제외 사유, 입력 보존을 확인한다.
기존 코드 수정은 같은 입력의 수정 전 실패와 수정 후 성공을 비교한다.
세부 점검은 [scenarios.md](scenarios.md)의 해당 유형만 읽는다.

서버는 공식 안내에 맞춰 0.0.0.0으로 바인딩하고 해당 터미널을 유지한다.
HTTP 확인과 실제 화면 확인을 구분하며 UI 조작은 응시자가 내장 Browser에서 한다.
스크린샷이나 보고서만으로 실제 동작을 확인했다고 쓰지 않는다.

## 6. 기능 동결과 제출 전 확인

계산한 기능 동결 시각부터 새 기능 추가를 멈추고 필수 요구의 실패를 해결한다.
메인 요청:

```text
지금부터 기능을 동결해.
REQUIREMENTS의 필수 항목마다 PASS / FAIL / NOT_RUN / HUMAN_CHECK와 실제 근거를 연결해.
문서에 적힌 실행 명령으로 핵심 흐름을 다시 실행하고 출력 경로, 형식, 파일 저장 상태를 확인해.
핵심 수치 하나는 작은 기준 사례로 검산해. 중요한 테스트가 잘못된 결과를 잡는지 확인해.
내가 알아야 할 미충족 요구와 한계, 제출할 파일을 짧게 정리해.
```

제출 시작 시각에는 다음을 확인한다.
- 실제 과제가 요구하는 파일과 실행 방법, 문서가 저장되어 있다.
- 예시 데이터나 다른 세션의 임시 결과를 최종 산출물로 착각하지 않는다.
- 원본, 결과물, 근거 기록을 불필요하게 삭제하지 않는다.
- 자기 구현의 핵심 동작, 선택의 이유와 한계를 제출 확정 전에 설명할 수 있다.
- 실제 검증하지 않은 항목과 남은 실패를 정확히 표시했다.

제출 버튼은 응시자가 직접 누른다. 제출 확정 이후에는 AI 작업과 답변 코칭을 멈추고 화면의 후속 절차를 따른다.
서술형은 AI와 복사 붙여넣기 없이 직접 작성한다.

## 7. 장애가 생겼을 때

| 상황 | 즉시 할 일 | 이어갈 경로 |
|---|---|---|
| clone 또는 설치 실패 | 에러와 현재 경로 확인, 기존 파일 보존 | 5분 안에 해결되지 않으면 최소 요청으로 시작 |
| 스킬이 보이지 않음 | 해당 .agents/skills/probe-*/SKILL.md 직접 읽기 | 일반 프롬프트로 동일 작업 수행 |
| codex 시작 실패 | 오류 기록과 공식 문제 신고, 필요 시 Helper 문의 | 버전이나 인증 설정을 임의 교체하지 않음 |
| 작업 세션 이용 불가 | 마지막 인계와 미커밋 변경 확인 | 메인이 같은 명세로 이어서 구현 |
| 컨텍스트 부족 또는 새 세션 | 자기 인계와 CURRENT 갱신 | 새 세션은 CURRENT → 해당 인계 → 관련 보고서 |
| 파일 동시 수정 | 편집을 멈추고 실제 diff와 소유 범위 확인 | 통합 담당자가 조정 후 편집 재개 |
| 같은 오류에 약 10분 | 재현, 현재 가설, 확인한 증거 정리 | 범위 축소 또는 업무 담당자 확인 |
| 화면 미리보기 실패 | 서버 유지, 포트와 바인딩 및 CLI/HTTP 결과 확인 | 응시자 수동 Browser 확인, 플랫폼 오류 신고 |
| 남은 시간이 짧음 | 실제 타이머로 제출과 서술형 여유 재확인 | 필수 흐름과 저장, 제출 우선 |

하네스 설치 없이 시작하는 최소 요청:

```text
공식 규칙과 과제 README를 먼저 읽어.
사실, 가정, 질문, 제외 범위, 검증 가능한 성공 기준을 짧게 정리해.
담당자 질문은 내가 전송하고 답을 파일에 남길게.
최초 계획 합의 후 대표 입력에서 출력까지 최소 흐름을 만들고 검증해.
실제 명령과 결과, 선택 이유와 한계를 기록해.
기능 동결과 제출 시각은 내가 알려준 실제 남은 시간에 맞춰 지켜.
```

## 실행 점검과 근거

하네스의 전체 흐름 점검은 [REHEARSAL.md](REHEARSAL.md)에 있다.
실제 모델 호출과 감독 연결은 로컬 점검의 범위가 아니다.
원본 비교는 [최신 확인 기록](references/upstream-check-20261031.md), 평가 의도는 [인터뷰 분석](references/cofa-probe-interview-20261031.md)을 참고한다.
Codex의 /model 명령은 [OpenAI 공식 문서](https://learn.chatgpt.com/docs/developer-commands?surface=cli)에 근거한다. 대회에서 실제 제공된 버전과 허용 목록이 우선한다.
