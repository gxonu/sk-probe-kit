# 코드 맥락에서 질문을 만드는 few-shot

아래 두 사례는 **질문 작성 방식을 보여 주기 위해 새로 구성한 가상 예시**다. 실제 시험 문제, 응시 기록, 실행된 코드가 아니다. 예시의 파일/함수는 현재 프로젝트에 존재하지 않는다. 새 질문의 근거는 반드시 현재 프로젝트에서 다시 찾아야 한다.

공통 작성 방식: 관찰한 구현 → 중요한 선택/경계 → 설명을 요구하는 질문. 실제 출제 예측이나 현재 프로젝트의 답변 근거가 아니다. 자료 모드에서는 실제 코드와 기록으로 주요 6문항과 보조 문항의 답변 초안까지 만든다.

## 예시 A: 생산 작업 배정

### 입력: 확인했다고 가정한 코드 맥락

- `demo/schedule.py::choose_assignment`: OR-Tools로 만든 작업 배정 후보와 순차 배정 기준안의 목적값을 비교해 사용할 계획을 선택한다.
- `demo/checks.py::check_assignment`: 기계 중복 사용과 작업 누락을 검사한다. 검사 코드의 존재만 확인했고 실행 로그는 없다.
- `demo/service.py::make_plan`: 요청을 정리하고 계산, 검사, 저장을 호출한다.
- 설정으로 계산 시간 제한을 받는다. 결과 재사용 기능은 이 예시 맥락에 명시돼 있지 않다.

### 출력: 위 맥락에 맞춘 예상 질문

1. **선택:** 두 배정안의 목적값을 비교하는 구조가 어떤 요구를 충족하려는 선택인지 설명해 주세요. 목적값과 규칙 준수의 관계, 다른 선택지, 이 방식으로 해결하지 못하는 경우도 설명해 주세요. 근거: `demo/schedule.py::choose_assignment`, `demo/checks.py::check_assignment`.
2. **구조:** 요청 하나가 저장 가능한 배정안이 되기까지 어떤 데이터를 거치나요? make_plan과 계산/검사 함수의 책임을 설명해 주세요. 근거: `demo/service.py::make_plan`.
3. **범위와 증거:** 검사 함수가 있다는 사실 외에 배정의 유효성을 확인한 근거는 무엇인가요? 아직 실행하지 않았다면 무엇을 어떤 입력으로 확인해야 하나요? 근거: `demo/checks.py::check_assignment`.
4. **예외:** 시간 제한 안에 후보가 나오지 않는 요청에서 현재 코드는 어떻게 처리되나요? 그 경로와 결과 상태를 어디서 확인할 수 있나요? 근거: `demo/schedule.py::choose_assignment`.
5. **추가 검증:** 설비 수나 작업 조건을 바꾼다면 어떤 검사를 우선하겠습니까? 계산 함수의 설명에 의존하지 않고 정답을 비교할 작은 사례를 어떻게 만들겠습니까? 근거: `demo/checks.py::check_assignment`.

6. **AI 협업:** 이 예시에는 협업 기록이 없다. 실제 프로젝트에서 배정 방식에 대한 AI 제안을 수용/수정/폐기한 사례가 있다면 무엇이며 근거는 무엇인가요?
   답변 초안: `[사용자 확인 필요]` AI의 제안과 사람의 판단 기록이 없으므로 선택 이유와 검증 성공을 작성할 수 없다.

예시는 실제 최적화 전략이나 재사용 기능, 처리 성공을 추정하지 않는다. 질문의 목적함수와 근거는 새로운 과제에서 다시 선택한다.

## 예시 B: 주문 CSV 정리와 보고서

### 입력: 확인했다고 가정한 코드 맥락

- `demo/clean.py::prepare_orders`: 주문 ID별 최신 행을 남긴 뒤 취소 주문을 제외한다.
- `demo/report.py::summarize`: 부서별 금액을 합산한다.
- `demo/export.py::write_report`: CSV를 저장한다.
- 검증 기록에는 샘플 행 수 비교만 있고, 금액의 독립 검산이나 같은 시각의 중복 처리 기준은 없다.
- 이 예시에 최적화 솔버, 로그인, DB는 없다.

### 출력: 위 맥락에 맞춘 예상 질문

1. **선택:** 최신 행 선택 후 취소를 제외하는 순서가 결과에 어떤 영향을 주나요? 반대 순서를 택했을 때 달라지는 입력과 현재 선택의 업무상 근거를 설명해 주세요. 근거: `demo/clean.py::prepare_orders`.
2. **구조:** 입력 열이 최종 보고서 열로 바뀌는 과정을 설명해 주세요. 전처리, 합산, 저장 단계 사이의 계약은 무엇인가요? 근거: `demo/clean.py::prepare_orders`, `demo/report.py::summarize`, `demo/export.py::write_report`.
3. **범위와 증거:** 현재 행 수 비교로 확인한 것과 금액 정확성에 대해 아직 확인하지 않은 것을 구분해 주세요. 다른 사람이 어떤 결과를 다시 확인할 수 있나요? 근거: 샘플 행 수 비교 기록과 `demo/report.py::summarize`.
4. **예외:** 같은 주문에 동일한 최신 시각의 행이 두 개 있으면 어느 행을 남기나요? 입력 순서가 달라져도 결과가 같은지 어디서 확인해야 하나요? 근거: `demo/clean.py::prepare_orders`.
5. **추가 검증:** 취소와 중복이 함께 있는 작은 입력으로 집계 금액을 어떻게 독립 검산하겠습니까? 어떤 결과가 나오면 현재 처리 순서를 재검토하겠습니까? 근거: `demo/clean.py::prepare_orders`, `demo/report.py::summarize`.

새 프로젝트에 이런 처리 순서나 검증 기록이 없으면 예시의 전제를 복사하지 않는다. 질문의 구조만 참고한다.

6. **AI 협업:** 실제 작업에서 AI가 제안한 정제 순서를 어떤 근거로 수용하거나 바꿨나요? 이 가상 입력에는 해당 협업 기록이 없으므로 답변은 사용자 확인 필요로 남긴다.

## 보조 문항과 답변 초안의 예시

예시 B의 P3 보조 질문: 행 수가 일치하면 금액 정확성도 확인된 것인가요?
답변 초안: 행 수 일치만으로 금액의 정확성을 확인할 수 없다. 알려진 작은 입력의 합계를 별도로 계산해 보고서와 비교해야 하며 이 예시에서는 그 검증이 실행되지 않았다.

예시 A의 P4 보조 질문: 계산이 시간 안에 끝나지 않으면 기존 결과가 보존된다고 설명해도 되나요?
답변 초안: 입력 맥락에는 기존 결과 보존 경로가 제시되지 않았다. 실제 저장/오류 경로를 읽기 전에는 보존된다고 단정할 수 없으며 확인해야 할 코드로 남긴다.

## 완성형 출력 예시: 질문과 답변을 함께 작성하기

아래 C~E도 전부 가상 사례다. 코드 경로, 기록 ID, 수치와 판단은 형식 설명용이며 현재 과제의 사실로 옮기지 않는다. 실제 자료 모드는 이 형식을 **P1~P6 각각에 적용해 주요 6문항 + 보조 12문항과 모든 답변**을 만든다. 현재 과제와 가까운 예시를 골라 형식과 근거 구분 방식을 참고한다.

## 예시 C: 선택 이유와 실제 검증 근거가 있는 경우

### 입력으로 주어진 가상 근거

- `sample/assign.py::choose_plan`: 순차 배정 기준안과 시간 제한을 둔 OR-Tools 후보를 만든다. 각각 필수 제약을 검사하고 유효한 후보 중 목적값이 낮은 결과를 선택한다.
- `sample/validate.py::check_plan`: 작업 누락과 같은 설비의 시간 중복을 검사한다.
- 가상 요구 `R-01`: 작업 누락과 설비 중복은 허용하지 않으며, 그 조건 안에서 완료 시각을 줄인다.
- 가상 결정 `D-01`: 사람이 첫 실행 가능한 결과를 확보하는 일을 우선해 시간 제한과 기준안 비교를 채택했다. 충분한 시간 동안 최적해를 찾는 방식은 이번 범위에서 제외했다.
- 가상 실행 근거 `EV-01`: 작은 입력 한 건에서 기준안 18분, 후보 15분, 두 결과의 필수 제약 위반 0건을 별도 검사기로 확인했다. 대규모 입력과 최적성 증명은 실행하지 않았다.

### 출력

**P1. 설계 선택**

**질문:** 순차 배정만 사용하는 대신 시간 제한을 둔 OR-Tools 후보와 비교한 이유는 무엇인가요? 필수 제약과 목적값의 관계, 제외한 대안, 이 선택의 한계와 다음 검증을 설명해 주세요.

**요구 요소:** 선택 이유 / 필수 제약과 개선 목표 / 대안과 한계 / 다음 검증.

**근거:** `sample/assign.py::choose_plan`, `sample/validate.py::check_plan`, 가상 `R-01/D-01/EV-01`.

**답변 초안:** 먼저 실행 가능한 결과를 확보하면서 완료 시각을 개선하려고 순차 배정과 시간 제한을 둔 후보를 비교했습니다. 작업 누락과 설비 중복은 먼저 검사하고, 이를 통과한 결과끼리만 목적값을 비교합니다. 충분한 시간 동안 최적해를 찾는 대안은 이번 시간 예산에서 제외했습니다. 작은 입력 한 건에서는 완료 시각이 18분에서 15분으로 줄었고 별도 검사에서 필수 제약 위반이 없었습니다. 다만 이 결과는 모든 입력의 개선이나 전역 최적성을 증명하지 않으며, 다음에는 규모 증가와 배정 불가능한 입력에서 실행 시간과 실패 처리를 확인하겠습니다.

**보조 질문 1:** 목적값이 더 낮지만 설비 사용 시간이 겹치는 후보는 선택해도 되나요?

**답변 초안:** 안 됩니다. 이 가상 요구에서 설비 중복은 필수 제약이므로 목적값 비교 전에 제외해야 합니다.

**보조 질문 2:** 시간 안에 유효한 후보가 하나도 나오지 않으면 기존 저장 결과는 유지되나요?

**답변 초안:** 제공된 근거에는 저장과 오류 처리 경로가 없습니다. 실제 서비스의 저장 호출과 실패 분기를 읽기 전에는 기존 결과가 유지된다고 단정할 수 없습니다.

**미확인:** 대규모 실행은 `NOT_RUN`, 실패 시 기존 결과 보존은 코드 확인 필요.

**이해할 핵심어:** 필수 제약, 목적값, 기준안, 시간 제한, 최적성의 한계.

## 예시 D: 코드만 있고 실행과 결정 이유가 부족한 경우

### 입력으로 주어진 가상 근거

- `demo/clean.py::prepare_orders`는 주문 ID별 최신 행 선택 후 취소 주문을 제외한다.
- `demo/report.py::summarize`는 부서별 금액을 합산한다.
- 기록에는 출력 행 수 비교만 있고 금액 독립 검산, 같은 시각의 중복 기준, 처리 순서를 선택한 사람의 이유는 없다.

### 출력

**P5. 위험과 독립 검증**

**질문:** 출력 행 수가 일치한다는 근거만으로 집계 금액도 정확하다고 할 수 있나요? 현재 검증의 범위와 취약한 조건, 독립적으로 확인할 입력과 수정 판단 기준을 설명해 주세요.

**요구 요소:** 확인한 범위 / 미검증과 취약점 / 독립 검산 / 수정 판단 기준.

**근거:** `demo/clean.py::prepare_orders`, `demo/report.py::summarize`, 가상 행 수 비교 기록.

**답변 초안:** 현재 기록으로 확인한 것은 출력 행 수이며 금액의 정확성은 아직 확인하지 않았습니다. 특히 최신 상태가 취소인 주문에서 정제 순서를 바꾸거나 같은 최신 시각의 행이 겹치면 결과가 달라질 수 있습니다. 주문 한 건의 이전 상태와 취소 상태를 포함한 작은 입력을 만들고 담당자가 확인한 기대 결과를 별개 계산으로 대조하겠습니다. 같은 시각의 행에 대한 기준은 아직 없으므로 임의로 정하지 않고 먼저 확인해야 합니다. 이 검증은 `NOT_RUN`이며 현재 처리 순서를 선택한 이유도 기록이 없어 사용자 확인이 필요합니다.

**보조 질문 1:** 검산 결과가 구현과 다르면 기대값을 구현에 맞춰 바꾸면 되나요?

**답변 초안:** 먼저 요구 근거와 기대값 계산을 다시 확인해야 합니다. 기대값이 확인된 요구와 맞으면 구현을 수정하고 같은 입력으로 재검증합니다.

**보조 질문 2:** 모든 입력에서 이 정제 순서가 맞다고 설명해도 되나요?

**답변 초안:** 현재 근거로는 그렇게 말할 수 없습니다. 업무상 상태 의미와 동점 처리 기준을 확인하고 해당 범위에서만 설명해야 합니다.

**미확인:** 금액 검산 `NOT_RUN`, 동점 기준과 처리 순서 선택 이유 `[사용자 확인 필요]`.

**이해할 핵심어:** 행 수와 금액 정확성의 차이, 독립 기대값, 상태 정정, 근거 없는 성공 주장.

## 예시 E: AI 제안에 대한 사람의 판단을 설명하는 경우

### 입력으로 주어진 가상 근거

- 가상 `Q-02`: 담당자가 입력은 한 번 받은 CSV이며 실시간 갱신은 필요 없다고 답했다.
- 가상 `D-02`: AI는 DB와 상시 갱신 작업을 제안했고, 사람은 Q-02와 남은 시간을 근거로 CSV 일괄 처리로 범위를 줄이기로 결정했다.
- 가상 `EV-02`: 대표 CSV 한 건의 실행과 출력 파일 생성은 확인했다. 대규모 파일 처리와 동시 요청은 미실행이다.

### 출력

**P6. AI 협업**

**질문:** AI의 제안을 그대로 적용하지 않고 범위를 바꾼 작업 하나를 설명해 주세요. 요구를 알게 된 경로, AI와 사람의 역할, 변경 이유와 실제 검증 범위를 포함해 주세요.

**요구 요소:** 요구 확인 경로 / AI와 사람의 역할 / 수용 또는 수정 이유 / 검증과 한계.

**근거:** 가상 `Q-02/D-02/EV-02`. 실제 프로젝트에서는 대응하는 기록과 구현 파일을 찾아 연결한다.

**답변 초안:** 담당자 답변 Q-02에서 한 번 받은 CSV를 처리하면 되고 실시간 갱신은 필요 없다는 점을 확인했습니다. AI는 DB와 상시 갱신 작업을 제안했지만, 저는 그 요구와 남은 시간을 근거로 CSV 일괄 처리로 범위를 줄이기로 결정했습니다. 따라서 AI 제안의 전체 구조를 채택하지 않고 필요한 처리 기능에 집중했습니다. 대표 입력 한 건에서 실행과 출력 파일 생성은 확인했습니다. 대규모 입력과 동시 요청은 검증하지 않았으며 요구가 바뀌면 저장 구조와 처리 방식을 다시 검토해야 합니다.

**보조 질문 1:** 이 선택이 토큰이나 비용을 얼마나 절약했나요?

**답변 초안:** 사용량 측정 기록이 없으므로 절감량을 수치로 말할 수 없습니다. 범위를 줄인 이유와 실제 측정 결과를 구분해야 합니다.

**보조 질문 2:** 같은 선택이면 언제나 더 단순한 구조가 낫나요?

**답변 초안:** 아닙니다. 지속적인 갱신, 여러 사용자의 동시 변경이나 이력 보존 요구가 생기면 이 선택의 전제가 달라지므로 대안을 다시 비교해야 합니다.

**미확인:** 처리 규모/동시 요청 `NOT_RUN`, 토큰/비용 절감량 측정 없음.

**이해할 핵심어:** 담당자 답변, AI 제안, 사람의 판단, 범위 조정, 검증 범위.
