# 구현을 바꾸는 조건을 찾는 질문

README와 데이터에서 직접 확인할 수 있는 것을 먼저 찾는다. 숨은 조건이 반드시 있다고 가정하지 않는다. 답이 달라지면 구현, 판정 또는 성공 기준이 바뀌는 질문을 우선한다.

## 질문을 고르는 순서

1. 현재 이해한 업무 목표를 한 문장으로 적는다.
2. 확인된 사실과 가정을 분리한다. 가정이 틀릴 때의 영향을 적는다.
3. 영향이 큰 미확인 사항을 최대 3개 고른다. 이미 받은 답은 다시 묻지 않는다.
4. 맥락이 부족하면 현재 업무와 실제 사례를 열린 질문으로 묻는다. 맥락을 확보한 뒤 선택지 A/B 또는 작은 입력과 기대 출력으로 조건을 좁힌다. 유도 질문으로 원하는 답을 강요하지 않는다.
5. 전송은 사람이 한다. 답을 기다리는 동안 원본 보존, 파일 구조 확인, 재현 명령 정리처럼 답과 독립적인 작업만 진행한다.

## 업무를 이해하는 첫 질문

현재 업무 → 최근 실패 사례 → 우선순위와 제약 → 구체적인 조건 → 이해 확인 순으로 필요한 질문만 고른다.
한 번에 최대 3개는 대화량을 관리하는 기준이며 전체 질문 수 제한이나 채점 공식이 아니다.

- 현재 누가 어떤 순서로 이 일을 처리하나요?
- 최근 가장 곤란했던 사례와 그 결과를 설명해 주실 수 있나요?
- 그 사례에서 어떤 실수의 피해가 가장 컸나요?
- 그러면 A를 우선하고 B는 제외하는 것으로 이해해도 될까요?

담당자에게 업무와 제약을 확인하고 해결 방향은 직접 제안한다. 해야 할 일 전체나 정답을 대신 정해달라고 요청하지 않는다.
이미 문서에서 확인한 내용은 반복해서 묻지 않는다. 받은 답이 바꿀 요구, 구현과 검증을 함께 적는다.

## 질문 은행: 해당하는 것만 사용

| 확인할 조건 | 질문 예시 | 답을 받으면 바뀌는 것 |
|---|---|---|
| 실제 의사결정 | 이 결과를 누가 보고 어떤 행동을 결정하나요? 오판 중 더 큰 피해는 무엇인가요? | 기능과 오류 우선순위 |
| 성공 기준 | 개선할 지표의 현재값, 목표값과 계산 대상은 무엇인가요? | 분모, 기준선과 검증 |
| 필수와 선호 | 반드시 지켜야 하는 조건과 가능하면 개선할 목표를 구분해 주실 수 있나요? | 제약과 최적화 목표 |
| 경계값 | 값이 기준과 정확히 같을 때 통과인가요? 이 한 행의 기대 결과를 확인해 주세요. | `<`와 `<=` 테스트 |
| 기준 적용 시점 | 기준 변경일에는 측정 시각, 판정 시각 중 무엇으로 적용 버전을 고르나요? 시간대는 무엇인가요? | 시간 결합과 정책 버전 |
| 중복 및 재측정 | 같은 ID의 여러 측정은 별도 사건인가요, 정정인가요? 최신값은 어떤 시각으로 정하나요? | 키와 중복 처리 |
| 결측 의미 | 이 빈 값은 미측정, 해당 없음, 수집 실패 중 무엇인가요? 보류 상태가 필요한가요? | 결측 처리와 불확실성 |
| 정보 이용 시점 | 이 열은 실제 결정을 내리는 시점에 이미 알 수 있는 값인가요? | 누수 방지와 평가 분할 |
| 예외 충돌 | 두 규칙이 충돌하는 이 사례는 어느 규칙이 우선인가요? | 판정 순서 |
| 제출 및 재현 | 필수 파일, 입력 방식, 실행 명령, 예상 데이터 크기를 확인해 주세요. | 출력 계약과 실행 검증 |

질문 예시는 실제 과제 조건이 아니다. 숫자, 단위, 규칙을 임의로 채우지 않는다.

## 답변 처리

`QUESTION_LOG.md`에는 Q-ID, 질문, 답변 출처, 확인 상태, 관련 R-ID, 테스트를 연결한다.
REQUIREMENTS.md의 관련 사실, 가정, 열린 질문과 사용자 행동에 미치는 영향을 갱신하고 결과를 바꾸는 결정은 DECISIONS.md에 남긴다.
답변이 모호하면 확정으로 표시하지 않는다. 규칙이 바뀌면 작은 입력의 기대 결과부터 확인한다.
여러 세션을 쓰면 작업 세션은 자기 인계 문서에 반영안을 남기고, 통합 담당자가 공통 원장에 반영한다.

합의한 목표가 데이터상 불가능하다면 결과를 꾸미지 않는다. A안의 충족 범위와 한계, B안에 필요한 추가 정보 또는 조건 변경을 정리해 사용자에게 전달한다.

구현 후 담당자에게 보낼 요약은 다섯 줄로 정리한다: 해결한 문제, 핵심 결과 수치, 검증 방법, 남은 한계, 확인받을 결정. 확인하지 않은 수치는 넣지 않으며 전송은 사람이 한다.
