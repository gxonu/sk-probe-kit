## 질문을 구현으로 연결하기

담당자에게 업무 맥락을 묻고 해결 방향은 스스로 정한다.
'해야 할 일을 순서대로 모두 알려달라'는 접근은 16:55에서 부정적으로 설명한다.
현재 업무 → 최근 실패 사례 → 우선순위와 제약 → 구체적인 입력과 기대 결과 → 이해 확인 순서를 권한다.
이 순서는 적용 제안이며 모든 질문을 다 해야 한다는 규칙이 아니다.

예시 질문:
- 현재 이 일을 누가 어떤 순서로 처리하나요?
- 최근 가장 곤란했던 사례 하나를 설명해 주실 수 있나요?
- 그 경우 어느 실수의 피해가 더 큰가요?
- 그러면 이번에는 A를 우선하고 B를 제외하는 것으로 이해해도 될까요?

답은 Q-ID → R-ID → 결정 → 코드 → 검증으로 연결한다.
질문 수, 고급 용어, 숨은 조건 발견 개수를 점수의 대리 지표로 삼지 않는다.
시연 과제의 조건 공개 방식을 모든 과제의 사실로 일반화하지 않는다.

## 인지와 설계 판단

읽기만 필요한 API에 쓰기 상황을 위한 과한 장치를 넣은 사례는 현재 요구에 맞는 설계를 판단해야 한다는 설명이다.
보안이나 데이터 일관성을 전반적으로 생략하라는 뜻으로 확대하지 않는다.

주요 선택에서 확인할 질문:
1. 어떤 사용자 요구 때문에 이 구조가 필요한가?
2. 더 단순한 대안은 어떤 조건에서 충분한가?
3. 현재 선택이 유효한 입력, 규모와 운영 조건은 무엇인가?
4. 어떤 조건이 바뀌면 선택을 재검토하는가?
5. 그 이유가 실제 코드와 실행 결과에 일치하는가?

설명이 막히면 기록 누락과 이해 부족을 구분한다. 관련 코드와 작은 입력을 확인하고 자기 말로 설명한 뒤 기록한다.
문장을 추가하는 것만으로 이해가 생겼다고 처리하지 않는다.

## 도메인 지식과 재사용

매장 경험자의 사례는 사용자 이해, 설계, AI 활용, 완성도 있는 결과가 함께 작용한 사례다.
반도체 자료도 용어를 나열하기보다 실제 의사결정, 데이터 의미, 오류 비용과 이용 가능 시점을 질문하는 데 활용한다.
임계값, 결측 처리, 재측정 정책을 일반 지식만으로 확정하지 않는다.

스킬과 하네스는 반복 설명과 재작업을 줄일 때 유용하다.
각 도구의 역할, 입력, 확인할 출력, 사용하지 않을 조건을 이해하고 필요한 것만 사용한다.
초기 설정 비용과 남은 시간까지 고려한다.

- DECISIONS: 이유에 업무 영향과 적용 조건, 한계에 재검토 조건을 포함.
- 설명 연습: 코드와 작은 입력을 통해 이해를 확인.
- 세션 공유: 현재 상태, 개별 작업 인계, 출처, 실행 보고서를 분리하고 파일 작성자를 지정.
