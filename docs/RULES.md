# 우선순위와 작업 원칙

## 우선순위

1. 운영팀의 최신 공식 안내와 응시 화면의 규정. 기존 문서와 충돌하면 최신 명시 안내를 따른다.
2. 실제 과제 README, 제출 규격, 업무 담당자가 확인한 요구사항. 운영 규칙을 완화하는 답변으로 해석하지 않는다.
3. 사용자가 승인한 합의문과 아래 작업 원칙.
4. 하네스, 공개 지식, 후기. 사실과 제안, 미확인을 구분하며 공식 채점 기준으로 단정하지 않는다.

충돌이 해소되지 않으면 임의로 우회하지 않고 해당 담당자에게 확인할 질문을 정리한다.

## 공식 안내에서 확인한 범위

근거: 2026-10-26 안내 메일과 첨부 가이드 3종, 우선 적용되는 2026-10-29 안내 메일.
개인 링크, 원본 메일, 신분증, 문제, 답안은 이 저장소에 포함하지 않는다. 당일 추가 공지는 응시자가 별도로 확인한다.

- 응시는 2026-10-31 10:00~14:00, 준비 접속은 09:40. 과제 최대 180분, 후속 서술형 6문항 각 5분. 늦게 시작해도 14:00 종료.
- 사전 체험은 1회 15분이다. 실제 장비에서 감독 연결과 작업 흐름을 확인한다.
- Chrome, 단일 모니터, 웹캠, 충전 중인 휴대폰과 Cofa Proctor, 안정적인 Wi-Fi, 실물 신분증을 준비한다. 블루투스 키보드와 마우스는 사용하지 않는다.
- 제공된 Codex만 사용하고 업데이트하지 않는다. 모델은 응시 환경 목록에서 선택한다. 권장 표기는 Sol 6.1, Terra 5.6, Luna 6.0이며 Astra는 사용 제한이다. 모델 ID나 추론 수준을 추정해 설정하지 않는다.
- 공개 저장소, Skill, MCP, Plugin은 허용 범위 안에서 활용한다. 사용한 저장소는 결과 통지 전까지 공개 상태를 유지해야 한다. 외부 자료로 결과물을 통째로 대체하지 않는다.
- 문제, 파일, 결과물의 외부 전송과 Git Push, 개인 PC 파일 업로드, 별도 AI 및 개인 API 키 사용은 금지다. 외부 브라우저로 자료를 직접 열지 않는다.
- 감독 및 보안 우회와 Computer Use는 사용하지 않는다. 플랫폼의 인증, 관리 설정, 연결 프로세스를 변경하거나 종료하지 않는다.
- 웹 서비스는 0.0.0.0에 바인딩하고 내장 Browser에서 응시자가 직접 확인한다. 서버 터미널을 유지한다.
- 과제 중 제출 문서 작성에는 AI를 활용할 수 있다. 후속 서술형은 AI와 복사 붙여넣기 없이 응시자가 직접 답한다.
- 사용법은 Cofa Helper, 업무 조건은 업무 담당자, 플랫폼 오류는 문제 신고로 문의한다. 재접속과 신고 중에도 타이머는 계속된다.
- 수집 대상에는 대화, 터미널, AI 설정, git 로그와 diff, 테스트 결과 및 작업 파일이 포함된다. 수집 대상이라는 사실이 특정 커밋 수나 문서에 가점이 보장된다는 뜻은 아니다.

## 사용자가 선택한 일곱 가지 작업 원칙

1. **구현 전에 묻기.** README를 먼저 읽고 미확인 조건을 찾는다. 질문 초안은 한 번에 최대 3개, 전송은 응시자가 한다. 답변을 REQUIREMENTS.md에 출처와 함께 남긴다. README가 반드시 불완전하다고 가정하지 않는다.
2. **합의 후 구현.** 사실, 가정, 열린 질문, 제외 범위, 측정 가능한 성공 기준을 정리하고 최초 계획 승인을 받는다. 승인된 범위 안의 수정은 반복 승인 없이 진행하며 범위가 달라질 때 재합의한다.
3. **작게 끝까지.** 시작 후 40분에 대표 입력부터 제출 형식 출력까지 첫 완주를 목표로 한다. 과제 특성에 따라 60분까지 조정하려면 이유를 기록한다. 140분부터 기능을 동결하고 170분까지 제출 절차에 들어간다. 절대 종료 시각도 함께 확인한다.
4. **수치는 코드로.** 계산, 집계, 규칙 판정은 재현 가능한 코드로 처리한다. AI는 해석과 초안에 활용하며, 데이터에 없는 기준을 만들어 넣지 않는다.
5. **실행 증거로 판단.** PASS / FAIL / NOT_RUN / HUMAN_CHECK를 구분한다. 실행 명령, 실제 출력, 결과 파일, 코드 위치를 기록한다. 핵심 계산은 독립된 작은 기준 사례로 검산한다. 중요한 테스트는 의도된 오류를 잡는지 확인하고, 구현값에 맞춰 기대값을 바꾸지 않는다.
6. **결정 기록.** DECISIONS.md에 선택, 버린 대안, 이유, 검증, 한계를 적는다. 설명은 구체적인 지점, 파급, 다음 확인 순서로 연습한다. 연습은 제출물 확정 전에 마친다.
7. **필요한 맥락만.** 큰 파일을 먼저 집계하고 필요한 범위만 읽는다. 세션을 바꾸기 전 HANDOFF.md에 현재 요구, 결정, 실행 결과, 남은 일과 시간을 기록한다. 새 세션이 자동으로 맥락을 안다고 가정하지 않는다.

## 메인과 서브

- 메인은 요구, 설계, TASK_SPEC, 결과 검토를 맡고 서브는 지정된 파일과 검증을 맡는다. 각각의 프롬프트는 `prompts.md`에 있다.
- 사용자가 서브를 시작한 경우에만 분업한다. 도구가 지원되지 않거나 시간 손해가 크면 메인이 직접 구현한다. 이 역할 분담은 공식 요구사항이 아니다.
- 메인은 SUB_RESULT 요약만 믿지 않고 중요한 코드 변경과 실제 실행 결과를 확인한다. 같은 파일을 두 세션이 동시에 수정하지 않는다.
- 기본 승인과 샌드박스 설정을 유지한다. 별도 설정 파일, 비표준 CLI 플래그, 자동 에이전트 실행은 설치하지 않는다.
- 의미 있는 단계에서 변경 파일을 검토한 후 필요한 파일만 로컬 커밋한다. 과제 지침이 다르면 그 지침을 따른다. 원격 push는 하지 않는다.
- 한 장애에 10분을 쓰면 원인과 대안을 보고하고 범위를 줄이거나 질문한다. 같은 실패 명령을 무한 반복하지 않는다.
