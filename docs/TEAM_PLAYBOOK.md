# 8개 세션의 역할과 소유권

사용자가 같은 과제 폴더에서 S1~S8을 직접 시작한다. 역할 수는 동시에 무거운 작업을 8개 실행하라는 뜻이 아니다. 시작 프롬프트와 진행 중 요청은 [foruser.md](../foruser.md)에 모은다.

| 세션 | 역할 | 소유 범위와 결과 |
|---|---|---|
| S1-main | 총괄과 통합 | CURRENT, REQUIREMENTS, DECISIONS, EVIDENCE와 작업자 TASK_SPEC. 질문 답변 수용, 요구/인터페이스 조정, 통합과 제출 판단 |
| S2-worker-a | 개발 A | 실제 과제에서 배정한 핵심 실행/처리 파일과 테스트 |
| S3-worker-b | 개발 B | S2와 겹치지 않는 화면/출력/별도 처리 단계와 테스트 |
| S4-data | 데이터와 알고리즘 | 작은 EDA, 단순 기준안, 독립된 작은 정답 사례, 측정한 개선. 담당자에게 물을 데이터 조건 |
| S5-research(조사와 문의) | 한정된 조사와 문의 | 질문 하나와 시간 예산에 맞춘 공식 자료/공개 레포 조사, 출처/적용 조건/권고. 실제 메시지는 사용자가 전송 |
| S6-review(독립 검증) | 독립 검증과 제약 점검 | 요구 누락, 반례, 상태/계산/입력 오류, 자원과 제출 확인. 재현 근거와 최소 수정 제안 |
| S7-records(기록과 제출 문서) | 기록과 제출 문서 | 각 세션의 실제 결과를 정리해 공통 원장 반영 제안. 배정받은 HOW_TO_RUN/AI_COLLABORATION 등 실제 필수 문서 작성 |
| S8-explain(서술형 대비) | 서술형 대비 | `$probe-explain`으로 코드 기반 주요 6문항, 보조 문항, 답변 초안과 이해도 피드백. 자기 SUB_RESULT에 저장 |

개발 과제가 서비스가 아니면 S2/S3를 계산과 출력 등 독립된 범위로 바꾼다. 필요한 작업이 없으면 WAITING으로 두며 S8도 주요 단계에서만 실행한다.
괄호 안 한글은 역할 표시다. 파일 경로와 세션 ID는 `S5-research`처럼 영문 부분을 사용한다. 실제 README가 요구한 HOW_TO_RUN.md와 AI_COLLABORATION.md는 S7이 작성하고, S6가 실제 실행과 내용의 정합성을 검증하며, S1이 최종 확인한다.

## 공유 규칙

- S1만 CURRENT와 공통 REQUIREMENTS/DECISIONS/EVIDENCE를 편집한다. S7은 자기 SUB_RESULT에 근거와 반영 제안을 모으고 S1이 수용한다. 별도 WORKLOG/RECORD_PROPOSALS 문서를 요구하지 않는다.
- QUESTION_LOG만 모든 세션이 question_log.py를 통해 추가한다. 저장 도구가 파일 잠금을 잡고 최신 내용을 읽어 Q-ID를 발행한다. 직접 동시에 편집하지 않는다. 진행 세션, 기록 세션, 답변 출처를 구분한다.
- 문답 저장과 요구사항 확정은 다르다. S1이 새 답변의 영향과 충돌을 확인해 REQUIREMENTS와 관련 명세를 갱신한다. 작업자는 다음 단계에서 관련 Q-ID와 명세를 다시 읽는다.
- TASK_SPEC은 S1이, SUB_RESULT는 각 세션이 쓴다. HANDOFF는 세션 교체/중단에 사용한다. 일반 진행은 SUB_RESULT에 다음 행동까지 적어 반복 문서를 줄인다.
- S6는 결함과 의심, 개선 의견을 구분한다. 재현 입력/명령, 기대/관찰 결과, 업무 영향과 우선순위를 남긴다. 수정은 코드 소유자에게 맡긴다.
- S7은 실제 실행 증거 없이 성공을 쓰지 않는다. AI 협업에는 사람의 요청/판단, AI 제안, 수용/수정/폐기와 이유, 코드 및 검증 근거를 연결한다.
- S8은 현재 코드와 증거를 직접 확인한다. 기록에 없는 이유는 확인 필요로 남기고 근거 없는 대체 알고리즘, 캐시, DB나 성공을 답변 초안에 만들지 않는다. 제품 코드와 공통 원장을 수정하지 않는다.

## 단계별 연결

1. 시작: S1 요구/배정, S4 데이터 요약, S7 제출 규격 확인, S6 핵심 제약 점검. S5는 질문이 있을 때 조사한다.
2. 최초 계획 합의 뒤: S2/S3/S4가 대표 입력의 전체 흐름을 구현한다. S8은 중요한 선택과 설명할 내용을 파악한다.
3. 첫 완주 뒤: S6가 독립 확인, S7이 근거 정리, S8이 문항과 답변 초안을 만든다. S1이 필수 개선을 배정한다.
4. 제출 예정 시각을 기준으로 정한 준비 시점: S8이 최신 코드 기준 6문항과 보조 문항을 정리한다. 기본 lead는 40분이고 사용자/남은 시간에 맞춰 변경한다.
5. 기능 동결 뒤: S6 필수 검증, S7 실행/협업 문서 정합성 확인, 개발자는 필수 수정, S8은 변경된 문항만 갱신한다. S1이 확인하고 사용자가 제출 완료 표시를 확인한다.

## 실행 자원

RAM 16GB에서 서버/포트/DB/출력 경로와 무거운 명령의 소유자를 CURRENT에 적는다. S4 대규모 처리와 S6 전체 테스트가 겹치면 순서를 조정한다. S8은 필요한 코드와 요약만 읽고 새 서버나 무거운 테스트를 실행하지 않는다.
