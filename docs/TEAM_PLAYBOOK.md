# 7개 세션 운영

기존 명세 → 구현 → 결과 검토 흐름을 유지하면서 역할을 나눈다. 세션 수는 처리 능력을 보장하지 않는다. 사용자가 같은 과제 폴더에서 필요한 세션을 직접 열고, 작업이 있을 때 실행한다. 사용자와 합의한 기본 구성은 아래 7개 역할이다. 공식 평가 기준이 아니며 실제 과제에 맞춰 쓰기 범위를 배정한다.

## 역할과 결과물

| 세션 | 역할 | 맡을 일 | 주 결과물/쓰기 범위 예시 |
|---|---|---|---|
| S1-main | 총괄과 통합 | 요구/질문 확정, 우선순위, 인터페이스와 파일 배정, 결과 수용, 제출 판단 | CURRENT, 공통 원장, 작업자 TASK_SPEC |
| S2-worker-a | 개발 A | 서비스의 API/저장/처리 연결 또는 과제의 핵심 실행 경로 | 배정된 구현 파일과 자기 테스트 |
| S3-worker-b | 개발 B | 화면/입출력/조회 또는 개발 A와 분리된 기능 | 별도 배정된 구현 파일과 자기 테스트 |
| S4-data | 데이터와 알고리즘 | 작은 요약으로 의미/이상점 확인, 단순 기준안, 측정에 근거한 알고리즘 개선 | 배정된 분석/계산 모듈, EDA/비교 보고서 |
| S5-research | 조사와 문의 초안 | 막힌 질문에 대한 공식 문서/공개 레포 조사, 업무/사용법 문의 초안 | 출처, 적용 조건, 최대 3개 후보와 권고 |
| S6-review | 독립 검증과 비판 검토 | 요구 누락, 반례, 계산/상태 오류, 실제 재현, 개선 전후 회귀 확인 | 자기 검증 코드/보고서, 근거 있는 발견 사항 |
| S7-records | 기록과 제출 문서 | 결정/검증 이력 정리, 근거 연결, 실제 요구된 제출 문서 작성 | 자기 WORKLOG와 반영 제안, 배정받은 제출 문서 |

위 파일 범위는 예시다. 과제 구조를 확인한 후 CURRENT와 TASK_SPEC에 실제 경로를 배정해야 쓸 수 있다. 서비스가 아니면 S2/S3를 처리 파이프라인/출력, 계산/보고서 등 독립되는 기능으로 바꾼다.

**6개만 사용한다면 S5를 상시 운영에서 빼고, 한정된 조사를 S1 또는 S4에 맡기는 안을 우선한다.** S6의 독립 검증과 S7의 기록은 유지한다. 문제가 단순하거나 세션 전환 비용이 크면 더 줄인다. 같은 번호에 다른 역할을 몰래 바꾸지 않고 CURRENT에 인계와 변경을 기록한다.

## 작업 순서와 활성화

| 단계 | 주요 작업 | 필요할 때 참여 |
|---|---|---|
| 요구 확인 | S1이 README/제출 규격, S4가 작은 데이터 요약, S7이 필수 문서/증거 항목 정리 | S6는 계획의 핵심 반례, S5는 답이 필요한 질문만 조사 |
| 최초 계획 합의 | S1이 입력/출력 계약과 파일 소유자를 확정 | S2/S3/S4가 의존성과 완료 기준 확인 |
| 첫 전체 흐름 | S2/S3의 독립 구현, S4의 단순 기준안, S1 통합 | S6가 대표 입력 검증, S7이 실행과 미완료 기록 |
| 개선 | 작동하는 기준안 위에서 S4가 개선, S2/S3 필수 기능 보완 | S6가 동일 입력으로 비교/회귀 확인, S5는 구체적 막힘만 해소 |
| 기능 동결 | S1이 범위를 닫고 S6가 중요한 실패 검증, S7이 제출 문서 확정 작업 | 구현 담당자는 필수 결함 수정 |
| 제출 전 약 20분 | S7이 현재 코드/증거 위치를 묶고 S6가 예상 5문항 생성과 피드백 | S1은 남은 시간과 제출 점검 관리 |

열어 둔 세션 수와 동시에 무거운 작업을 실행하는 수는 다르다. 데이터 요약, 테스트, 빌드, 솔버를 무조건 동시에 실행하지 않는다. 자원 경쟁이 생기면 S1이 우선순위를 정한다.

## S1의 병목 줄이기

- 기능 하나하나를 구두 중계하기보다 TASK_SPEC에 입력/출력 계약, 쓰기 경로, 완료 기준을 함께 준다.
- 소유자가 자기 범위의 일반적인 구현 선택을 처리하고, 공통 계약/요구/범위 변경만 S1에 올린다.
- 결과는 먼저 상태, 핵심 변경, 검증, 막힘/요청을 요약하고 근거 파일을 연결한다.
- S1은 중요 변경과 실제 증거를 확인한다. 모든 로그를 다시 작성하지 않는다.
- 사용자는 담당자 답변, 중요한 방향 선택, 실제 화면 확인, 제출을 맡는다. 세션 간 합의를 위해 모든 대화를 복사할 필요는 없다.
- 파일 저장은 자동 알림이 아니다. 단계 완료 시 결과 경로를 전달하고, 수신 세션이 새 턴에서 읽는다. 백그라운드 감시나 자동 메시지 전송을 가정하지 않는다.

## 충돌을 막는 소유권

### 코드와 실행 자원

1. 같은 파일에 동시에 쓰는 세션은 하나다. “둘 다 백엔드” 같은 넓은 배정 대신 실제 파일/모듈로 나눈다.
2. API 스키마, DB 모델, 의존성/잠금 파일, Dockerfile, 공통 설정은 각각 소유자 한 명을 정한다. 변경이 필요한 다른 세션은 제안으로 전달한다.
3. S4가 계산 모듈을 맡으면 S2는 그 모듈을 호출하는 연결부를 맡는다. S2와 S4가 같은 알고리즘 파일을 따로 개선하지 않는다.
4. 공유 서버, 포트, DB, 테스트 출력 경로의 관리자를 CURRENT에 적는다. 검증 세션이 구현 담당자의 실행 서버나 DB를 초기화하지 않는다.
5. 독립 검증은 가능한 한 별도 입력/임시 DB/출력 경로에서 수행한다. 성능을 비교할 때는 동시 무거운 작업의 영향을 확인한다.
6. 완료 기준에는 실제 실행과 미검증을 구분해 적는다. 문서에 PASS라고 썼다는 이유로 완료를 수용하지 않는다.

### 공통 원장과 기록 담당

- S1만 CURRENT와 공통 REQUIREMENTS, QUESTION_LOG, DECISIONS, EVIDENCE의 최종 내용을 쓴다.
- S7은 자기 `docs/reports/S7-records/WORKLOG.md`와 `RECORD_PROPOSALS.md`에 근거를 모은다. 각 제안에 요구/작업 ID, 원출처, 확인 시각과 상태를 붙인다.
- S7은 “다른 세션이 PASS로 보고함”과 “실제 로그/출력을 확인함”을 구분한다. 사용자 결정 이유가 없으면 만들어 넣지 않는다.
- S1이 제안을 검토해 공통 원장에 반영한다. 원장 전체를 S7이 별도로 복제하지 않는다.
- 실제 README가 요구하는 HOW_TO_RUN, AI_COLLABORATION 등의 제출 파일은 S7에 독점 배정할 수 있다. S1은 검토 의견을 주고 S7이 수정한다. S1이 편집을 인수할 때는 소유권을 먼저 바꾼다.
- S7이 대신 기록하더라도 구현 담당자의 SUB_RESULT에는 실행 명령, 결과, 실패와 한계가 있어야 한다.

## 비판 검토를 유용하게 만드는 규칙

S6는 처음에는 계획의 위험, 첫 완주 뒤에는 동작, 개선 뒤에는 회귀, 기능 동결 뒤에는 필수 요구와 제출 가능성을 확인한다. 모든 단계에서 전체 코드를 다시 검토하지 않는다.

발견 사항의 형식:

```text
ID / 중요도 / 확인됨 또는 의심
관련 요구와 실제 파일:행
재현 입력과 명령
기대 결과 / 관찰 결과
업무 또는 제출에 미치는 영향
권장 최소 수정 또는 다음 확인
```

- 높은 우선순위: 필수 요구 실패, 잘못된 판정, 데이터 손실, 실행/제출을 막는 문제.
- 그다음: 특정 경계 입력의 오류, 중요한 성능/상태 문제.
- 개선 의견: 명명, 추상화, 미래 확장. 마감에 영향을 줄 때는 결함과 분리해 나중으로 둔다.
- 재현하지 못한 우려는 의심으로 표시한다. 문제가 없으면 확인한 범위와 남은 한계를 보고하고 끝낸다.
- 수정은 원래 코드 소유자에게 맡긴다. S6는 자기 검증 코드와 보고서를 쓰며, 필요하면 S1이 수정 범위를 새로 배정한다.
- S1이 처리 우선순위를 결정한다. 안전장치나 추상화를 늘리기 위한 무한 토론으로 첫 완주를 지연하지 않는다.

## S5 조사와 S4 개선의 종료 조건

S5는 질문 하나와 시간 예산을 받고 시작한다. 예를 들어 5~8분 안에 관련 출처 최대 3개, 적용할 부분, 의존성/제약, 가장 단순한 대안을 보고한다. 답을 찾지 못했으면 미확인으로 종료한다. 무기한 “유용한 레포 찾기”를 수행하지 않는다.

검색에는 일반 기술 질문을 쓰고, 실제 시험 문제/입력/코드를 외부 서비스에 전송하지 않는다. 업무 조건은 담당자에게 물을 초안으로 만들고 전송은 응시자가 한다. 도구 설치나 큰 의존성 추가를 조사 결과만으로 실행하지 않는다.

S4는 작은 데이터 요약과 기준 동작을 먼저 제공한다. 개선은 동일한 입력, 설정, 평가 기준에서 정확성/품질과 실행 시간을 비교하고, S6가 중요한 제약을 별도로 확인한다. 개선 효과가 없거나 일정에 맞지 않으면 현재 기준안을 유지한다. 데이터에 없는 기준을 조용히 만들어 넣지 않는다.

## 세션별 시작 요청

공통으로 공식 규칙, `.probe-kit/AGENTS.override.md`, 프로젝트 루트 `docs/handoff/CURRENT.md`와 자기 TASK_SPEC을 읽는다. 아래 요청은 실제 파일 배정 뒤 입력한다.

### S1-main

```text
S1-main으로 총괄해. 실제 README와 제출 규격을 읽고 요구, 시간, 계획을 정리해.
S2/S3 개발, S4 데이터/알고리즘, S5 한정된 조사, S6 독립 검증,
S7 기록/제출 문서의 기본 7개 역할을 적용하고 과제에 맞는 파일 범위를 제안해.
최초 계획 합의 후 CURRENT에 실제 파일과 실행 자원 소유자를 배정하고
세션별 TASK_SPEC을 작성해. 공통 원장은 네가 관리해.
결과 검토와 최종 선택을 맡되 각 담당자의 일반 구현 선택은 맡겨 둬.
```

### S2-worker-a / S3-worker-b

```text
나는 [S2-worker-a / S3-worker-b]야. 자기 TASK_SPEC의 구현과 검증을 맡아.
입출력 계약과 파일 범위를 지키고 공통 파일 변경은 소유자에게 제안해.
작은 입력의 실제 흐름부터 연결하고 SUB_RESULT에 명령, 출력, 실패와 한계를 남겨.
```

### S4-data

```text
S4-data로 배정된 데이터/계산을 맡아. 큰 파일은 작은 요약으로 먼저 확인해.
의미가 모호한 조건은 질문 후보로 남기고 단순 기준안부터 연결해.
개선은 같은 입력/설정에서 기준안과 비교하고 정확성과 시간을 분리해서 보고해.
배정된 계산 모듈만 수정하고 연결부나 공통 원장은 건드리지 마.
```

### S5-research

```text
S5-research로 이번 질문 [질문]만 [분]분 안에 조사해.
공식 문서와 관련 공개 코드에서 후보 최대 3개, 적용 범위와 비용을 보고해.
업무 조건은 문의 초안으로 만들고 직접 전송하지 마.
결과는 자기 보고서에 남기고 현재 작업에 쓸 결론 또는 미확인으로 마쳐.
```

### S6-review

```text
S6-review로 현재 [계획 / 첫 완주 / 개선 결과 / 제출 전]을 독립 검토해.
실제 요구 위반과 재현 가능한 반례를 우선하고, 증거와 최소 수정 방향을 보고해.
작업자의 주장과 실제 결과를 구분해. 의심은 확정 결함처럼 쓰지 마.
제품 코드 수정은 소유자에게 맡기고 배정된 검증 범위에서만 실행해.
```

### S7-records

```text
S7-records로 새 SUB_RESULT와 실제 코드/로그를 확인해 작업 이력을 정리해.
선택, 대안, 검증과 한계를 출처/시각/코드 기준과 함께 자기 보고서에 남겨.
공통 원장은 S1에게 반영안으로 전달하고, 실제 배정받은 제출 문서만 직접 써.
실행하지 않은 검증이나 확인하지 않은 사용자 판단을 사실로 채우지 마.
```

## 제출 전 예상 문항

S7은 최신 사실과 증거 위치를 제공하고, S6는 실제 코드도 읽어 예상 5문항을 만든다. 기록을 만드는 역할과 그 기록을 검토하는 역할을 구분한다. S6가 없으면 S1이 맡는다.

[출제 절차](mock-exam.md), [출제 프롬프트](../prompts/mock_exam_5.md), [일반화된 few-shot](mock-examples.md)을 사용한다. 질문 생성 3분, 직접 답변 7분, 피드백 4분, 제출 점검 6분을 기본 예시로 두되 실제 남은 시간에 맞춘다.
