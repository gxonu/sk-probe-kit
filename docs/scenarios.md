# 필요한 유형만 선택하기

시작은 데이터, 목표와 출력 계약이다. Case 분류를 끝내야 구현할 수 있는 것은 아니다. 아래는 원본의 9개 분류를 유지한 참고표이며 실제 출제 확률을 뜻하지 않는다.

| 유형 | 실제 과제에서 필요한 부분 | 참고 안내 |
|---|---|---|
| Case 1 | 데이터 정제/집계/리포팅 | [데이터](../skills/case1_data_pipeline.md) |
| Case 2 | 웹 서비스/웹앱 | [서비스](../skills/case2_web_service.md) |
| Case 3 | 기존 코드 오류/기능 수정 | [기존 코드](../skills/case3_legacy_debug.md) |
| Case 4 | 업무 자동화/운영 도구 | [규칙 판단](../skills/case4_policy_rag_doc.md), 필요한 데이터/서비스 부분 |
| Case 5 | 제조/반도체 데이터 판정 | [데이터](../skills/case1_data_pipeline.md), 실제 용어가 나오면 선택 설치 지식 검색 |
| Case 6 | 정책 문서 판단/보고 | [규칙 판단](../skills/case4_policy_rag_doc.md) |
| Case 7 | 검색/분류/챗봇 | [규칙 판단](../skills/case4_policy_rag_doc.md), 허용 환경과 필요성부터 확인 |
| Case 8 | 대안 비교/의사결정 | [규칙 판단](../skills/case4_policy_rag_doc.md), 기준과 가중치 근거 |
| Case 9 | 복합 처리 | 필요한 부분만 조합, 단계별 입력/출력 계약부터 배정 |

과제 조건 질문은 [interview](interview.md), 역할과 소유권은 [TEAM_PLAYBOOK](TEAM_PLAYBOOK.md) 한 곳에서 관리한다. Case 문서가 다른 운영 프로토콜을 만들지 않는다.
